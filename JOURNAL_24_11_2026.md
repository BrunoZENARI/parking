## 2. Réflexion sur les règles métier

### 2.1 Modélisation des entités

**Décision clé** : les places sont gérées par **nombre disponible par catégorie**, pas nominalement (pas de table `Place` avec un identifiant par place physique pour le MVP).

Entité centrale : `Category` — un compteur par type de place.

**Catégories définies :**

| Catégorie | Total | Walk-in | Booking |
|---|---|---|---|
| STANDARD | 80 | 70 | 10 |
| XL | 12 | 10 | 2 |
| ELECTRIC | 12 | 12 | 0 |
| HANDICAPPED (affiché « PMR ») | 6 | 6 | 0 |
| TWO_WHEELS | 10 | 10 | 0 |
| **Total** | **120** | **108** | **12** |

> Mise à jour du 28 octobre 2026 : XL passe de 12/0 à 10/2 pour permettre au service Réservation de réserver des places XL (voir section 18).

**Attributs de `Category` :**
- `name` — nom de la catégorie
- `total_capacity` — capacité totale fixe
- `walkin_capacity` — places allouées au walk-in
- `booking_capacity` — places allouées au booking
- `spot_taken_walkin` — stock réel walk-in (places confirmées occupées)
- `spot_available_walkin` — stock virtuel walk-in (tient compte des holds)
- `spot_taken_booking` — stock réel booking
- `spot_available_booking` — stock virtuel booking

**Invariant principal :**
```
walkin_capacity + booking_capacity = total_capacity  →  toujours vrai
```

### 2.2 Mécanisme de hold temporaire

Pour éviter les race conditions lors des entrées simultanées, mise en place d'un **stock réel vs stock virtuel** :

| Action | Stock virtuel (`spot_available_*`) | Stock réel (`spot_taken_*`) |
|---|---|---|
| Demande de hold | -1 | inchangé |
| Confirmation entrée | inchangé | -1 |
| Expiration hold | +1 | inchangé |
| Sortie | +1 | +1 |

> Correction du 18 novembre 2026 : le tableau ci-dessus décrit les variations de manière approximative. Dans le code, `spot_taken_*` compte les places occupées : l'entrée confirmée fait **+1** sur `spot_taken_*` (et ne touche pas le stock virtuel, déjà décrémenté par le hold), la sortie fait **-1** sur `spot_taken_*` et **+1** sur `spot_available_*`. Voir le tableau du README.

Entité `TemporaryHold` :
- `id`
- `category_id` — FK vers Category
- `commercial_type` — walkin ou booking
- `status` — active, confirmed, expired
- `created_at`
- `end_at` — moment d'expiration (30 secondes par défaut)

Le service gère lui-même l'expiration des holds (lazy cleanup à chaque requête).

### 2.3 Règles métier de modification de répartition

Lors d'une modification de `walkin_capacity` / `booking_capacity`, la contrainte à valider :
```
new_walkin_capacity >= spot_taken_walkin + holds_actifs_walkin
new_booking_capacity >= spot_taken_booking + holds_actifs_booking
```
On ne peut pas réduire une capacité en dessous du nombre de places déjà engagées (occupées + holds en cours).

### 2.4 Mutex

Chaque `Category` possède son propre `asyncio.Lock()` pour sérialiser les opérations concurrentes et éviter les race conditions sur le stock.

```python
async with self._lock:
    if not self.is_available(commercial_type):
        return False
    self.spot_available_walkin -= 1
    return True
```

### 2.5 Frontières de responsabilité

- **Blacklist mauvais payeur** → appartient à Paiement et Accès, pas à Parking
- **Vérification carte handicapé** → contrôle externe (ANTS), Parking ne stocke pas de données de santé (RGPD)
- **Règles de compatibilité véhicule/place** → appartient à Accès (un 2 roues peut prendre une place 4 roues, etc.)
- **Stationnement en cours** → appartient à Accès
- Parking reçoit uniquement un `category_name` et un `commercial_type` — il ne connaît pas le véhicule

## 3. Architecture et flux inter-services

### Rôle de Parking dans le flux global

Parking est un service **passif** — il répond aux demandes, n'initie rien.

**Appels synchrones REST (réponse immédiate nécessaire) :**
- Access → Parking : disponibilité d'une place
- Access → Parking : création d'un hold

**Événements asynchrones RabbitMQ (faits accomplis) :**
- Access → Parking : confirmation d'entrée
- Access → Parking : confirmation de sortie
- Booking → Parking : réservation confirmée (décrémente stock booking)

### Flux entrée/sortie

**Entrée :**
1. Access appelle `GET /parking/availability/{category}/{commercial_type}`
2. Access appelle `POST /parking/hold` → reçoit un `hold_id`
3. Barrière s'ouvre
4. Access publie `vehicle.entry.confirmed` → Parking confirme l'entrée en base

**Sortie :**
1. Access publie `vehicle.exit.confirmed` → Parking libère la place

Basée sur le modèle fourni par le professeur, corrigé et étendu :

```python
class Category:
    def __init__(self, name, total_capacity, walkin_capacity, booking_capacity, ...):
        # Invariant vérifié à l'instanciation
        if walkin_capacity + booking_capacity != total_capacity:
            raise ValueError(...)
        self._lock = asyncio.Lock()  # Un mutex par catégorie

    async def take(self, commercial_type) -> bool: ...      # Décrémente stock virtuel
    async def confirm_entry(self, commercial_type): ...     # Décrémente stock réel
    async def free(self, commercial_type): ...              # Libère stock réel + virtuel
    async def release_hold(self, commercial_type): ...      # Libère hold expiré
    def occupation_rate(self) -> float: ...                 # taken / total
```

## 3 novembre 2026 — Sécurité de la base Supabase

## 22. Alerte RLS du Security Advisor

- **Constat** : le Security Advisor de Supabase signalait 2 erreurs « RLS Disabled in Public » sur `public.categories` et `public.temporary_holds`. Supabase expose les tables du schéma `public` via une API REST publique (PostgREST). Sans RLS (Row Level Security), n'importe qui disposant de la clé publique du projet pouvait lire ou modifier ces tables sans passer par la clé d'API du micro-service.
- **Correction** : activation du RLS sur les deux tables, sans créer de policy, depuis le SQL Editor :
  ```sql
  ALTER TABLE public.categories ENABLE ROW LEVEL SECURITY;
  ALTER TABLE public.temporary_holds ENABLE ROW LEVEL SECURITY;
  ```
  Sans policy, l'API publique n'a plus accès à rien.
- **Pourquoi l'application n'est pas touchée** : elle se connecte directement à PostgreSQL via l'URL du pooler, avec le rôle propriétaire des tables, et pas par l'API REST. Le RLS ne s'applique donc pas à ses requêtes.
- **Vérification** : le Security Advisor n'affiche plus d'erreur après rafraîchissement, et le dashboard en production affiche toujours les 5 catégories.
- **Bonne pratique retenue** : toute table créée dans le schéma `public` de Supabase doit avoir le RLS activé, même si l'application n'utilise pas l'API REST.

## 25. Bugs sur les holds expirés

Découverts en testant le panneau d'actions (un hold sans confirmation ne rendait jamais sa place) :

- **`await` manquant** : dans `_cleanup_expired_holds`, l'appel à `category.release_hold(...)` n'était pas attendu alors que la méthode est `async`. Python affichait « coroutine was never awaited » et la place n'était jamais rendue : le hold passait en `expired` en base, mais le stock virtuel restait décrémenté. Des places étaient donc perdues de façon permanente. Corrigé avec `await`.
- **Mauvaise catégorie** : le nettoyage rendait toutes les places expirées à la catégorie de la requête en cours, même si le hold concernait une autre catégorie. Corrigé en filtrant sur `hold.category_id`.
- **Nettoyage plus fréquent** : le nettoyage est maintenant aussi déclenché par `/parking/occupation` et `/parking/occupation/{category}`. Avant, seuls `/availability` et `/hold` le faisaient, donc un hold expiré restait visible sur le dashboard.
- **Dates sans fuseau** : `datetime.utcnow()` (dépréciée) produisait des `RuntimeWarning` à chaque requête, car Tortoise travaille avec des dates avec fuseau. Remplacée par `datetime.now(timezone.utc)` dans le repository et dans `create_hold`.

## 26. `confirm_entry` exige un hold actif

- **Problème** : `confirm_entry` ne recevait qu'une catégorie et un type. On pouvait valider une entrée sans hold, ou deux entrées avec un seul hold, ce qui faussait le stock et contredisait le cœur métier (hold, entrée, sortie).
- **Règle** : `confirm_entry` reçoit maintenant le `hold_id` renvoyé par `/hold` et vérifie que le hold :
  - existe (sinon `404`) ;
  - correspond à la catégorie et au type demandés (sinon `409`) ;
  - est encore actif, ni expiré ni déjà utilisé (sinon `409`).
  Le hold passe ensuite à `confirmed` et ne peut plus être réutilisé. Un `hold_id` manquant renvoie `422`.
- **Impact sur le contrat avec Access** : l'appel `POST /parking/confirm_entry` doit désormais contenir `hold_id` (voir section 11 pour l'ancien format). À communiquer à Access.
- **Dashboard** : retient le dernier hold créé et l'envoie à la validation d'entrée, puis l'oublie. Il refuse l'action sans hold.
- **Durée d'un hold** : déjà configurable par la variable d'environnement `HOLD_TIMEOUT_SECONDS` (Render : onglet Environment, redémarrage automatique). Modification à chaud depuis le dashboard envisagée, non retenue pour l'instant.

## 27. Logs et correlation ID

- Nouveau module `infrastructure/api/logging_config.py` : configuration des logs et middleware `CorrelationIdMiddleware`.
- **Correlation ID** : repris de l'en-tête `X-Correlation-ID` s'il est valide (lettres, chiffres, `.`, `_`, `-`, 64 caractères maximum), sinon généré. Un identifiant invalide est ignoré, pour éviter l'injection dans les logs. Il apparaît dans chaque ligne de log et est renvoyé dans l'en-tête de la réponse. Parking n'appelle aucun autre service : il n'a donc pas à le propager plus loin.
- **Logs HTTP** (`parking.http`) : méthode, chemin, code et durée. `/health` et `/parking/occupation` (appelés en boucle par le dashboard) sont au niveau DEBUG.
- **Logs métier** (`parking.metier`) : hold créé, hold refusé (plus de place), hold expiré et place rendue, entrée confirmée, place libérée.
- Aucune donnée personnelle dans les logs.
- Exemple :
  ```
  2026-11-18 11:26:30,311 INFO [cb6ee1a1...] parking.metier: hold 23 créé (STANDARD/walkin)
  2026-11-18 11:26:30,311 INFO [cb6ee1a1...] parking.http: POST /parking/hold -> 201 (28.9 ms)
  ```

## 32. Bug de concurrence : stock Standard à 86/80

**Symptôme.** Le dashboard affichait Standard à 108 % : 86 places occupées pour une capacité de 80.

**Observations.**
- Les logs Render montraient des rafales de `POST /parking/free` (PMR, XL), un appel toutes les 100 à 200 ms, envoyées par les scripts de test d'autres services.
- De mon côté, je faisais des clics très rapides sur « Réserver » puis « Valider l'entrée » depuis le dashboard.

**Fausse piste.** J'ai d'abord soupçonné `free` d'accepter de libérer des places non occupées. Après lecture du code, `free` est protégé (il ne fait rien si `spot_taken` vaut 0) : ce n'était pas la cause.

**Diagnostic.** Dans Supabase, la ligne STANDARD donnait `spot_taken_walkin = 76` pour une capacité de 70 (avec `spot_available_walkin = 0`), alors que le booking était correct (10/10). Six entrées en trop. Les opérations sur le stock se font en trois temps (lire, modifier, sauvegarder) et le verrou de `Category` ne couvre pas toute cette séquence entre deux requêtes. Deux requêtes simultanées pouvaient donc rendre deux fois la place d'un même hold expiré, ou confirmer deux fois le même hold.

**Corrections.**
1. Un verrou global (`_stock_lock`) appliqué à tout le router via la dépendance `serialize_stock` : une seule opération sur le stock à la fois. Valable tant qu'il n'y a qu'une instance Render.
2. Garde-fous dans le domaine : `confirm_entry` renvoie `False` quand la capacité est atteinte (la route répond `409`, « Capacité atteinte, entrée refusée »), et `release_hold` ne peut plus dépasser `capacité - places occupées`.
3. Remise à zéro de la ligne STANDARD en base par un `UPDATE`.

**Vérification.** Après déploiement, clics rapides sur le dashboard de la prod : le compteur s'arrête à 80/80 et les clics suivants reçoivent un `409` (log « hold refusé : plus de place »). 45 tests passent.

**Leçons.**
- Les invariants (places occupées + disponibles + en attente = capacité) doivent être protégés dans le domaine, pas seulement par le déroulement normal des appels.
- Mon premier diagnostic était incomplet : c'est la lecture de la base qui a permis de trancher.
- Limite connue : un verrou en mémoire ne protège pas plusieurs instances. Avec plusieurs instances, il faudrait un verrou en base (`SELECT ... FOR UPDATE`).
